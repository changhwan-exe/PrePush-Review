# 프로젝트 기준 (찬반 리뷰용)

리뷰 세션들(반대파 · 찬성파 · 수정 담당)이 맨 먼저 읽는 문서. 세션은 이 프로젝트를 처음 보므로, **여기 적지 않은 것은 모른다.**
아래 네 절을 이 프로젝트에 맞게 채운다. 비워 둬도 돌지만, 의도된 동작이 버그로 보고되고 프로젝트 규칙 위반은 놓친다.
오탐이 나올 때마다 3절에 한 줄씩 더하면 다음부터 나오지 않는다.

## 1. 기준 문서

코드와 문서가 다르면 문서가 옳다. 리뷰 세션이 열어 볼 문서를 경로로 적는다.

<!-- 예
- 동작 명세: `docs/spec/*.md`
- 코드 규칙: `docs/CODE_CONVENTION.md`
- 구조 · 계층: `docs/architecture.md`
-->
- (없음)

## 2. 찾을 것

기본 스킬 `code-review` 는 일반적인 버그와 `CLAUDE.md` 규칙만 본다. 이 프로젝트에서만 문제가 되는 것을 항목 이름과 함께 적는다.
반대파가 diff 를 이 목록에 대어 보고, 위반을 코드 위치로 보일 수 있으면 문제(`C-`)로 올린다.

<!-- 예
- **권한**: 서버 검증 없이 클라이언트 값을 그대로 믿는 경로, 권한 확인이 빠진 관리자 API
- **계층**: 도메인 계층이 UI · DB 드라이버를 직접 참조하는 경우
- **자원**: 구독 · 해제 짝이 안 맞음, 닫지 않은 핸들
-->
- (없음)

## 3. 문제로 보지 말 것

의도된 동작, 알려진 한계, 아직 정해지지 않은 값. 여기 적힌 것은 지적하지 않고, 지적이 나오면 찬성파가 이 절을 근거로 반박한다.

<!-- 예
- 테스트용 계정 · 더미 데이터가 코드에 들어 있다 (출시 전 교체 예정)
- 재시도 횟수 · 시간 제한 값은 아직 정해지지 않았다 — 값 자체는 지적하지 않는다
- 이미 알려진 문제는 `docs/TODO.md` 에 있다 — 거기 적힌 것은 다시 보고하지 않는다
-->
- (없음)

## 4. 수정할 때 지킬 것

수정 담당이 따르는 규칙. 언어 버전, 건드리면 안 되는 폴더, 바꾸면 안 되는 이름 등.

<!-- 예
- C# 9 까지만 쓴다. 파일 인코딩(UTF-8 BOM)을 유지한다
- `vendor/` · `generated/` · `*.meta` 는 건드리지 않는다
- 직렬화되는 필드 · 공개 API 의 이름은 바꾸지 않는다
-->
- (없음)
